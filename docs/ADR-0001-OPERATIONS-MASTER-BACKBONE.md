# ADR-0001｜《貨達營運總表》作為營運中台管理骨架

- 狀態：Accepted
- 決策日期：2026-09-22
- 決策者：Jacky
- 影響範圍：PRD、SDD、資料模型、API、Dashboard、Tasks、權限與驗收

## 1. 決策

《貨達營運總表》不是另一套獨立系統，而是「貨達營運中台」的管理骨架。

- **營運總表＝定義公司要管理什麼。**
- **營運中台＝承載、更新、追蹤、提醒、分析與執行這些資訊。**

營運總表會在原營運管理 Session 持續累積；營運中台以受控匯入、同步或人工確認方式逐步承接。任何模組在中台正式驗收前，營運總表仍是該管理定義的主要來源；驗收後中台成為正式管理介面，但不得刪除與原來源的關聯。

## 2. 為什麼做此決策

現有中台已能收集 LINE、Gmail 與 GoWarehouse 匯出資料，也能整理情報與營運指標；但如果沒有共同管理骨架，容量、問題、SOP、KPI、客戶導入、人員與任務容易各自發展，造成重複輸入、定義不一致與歷史不可追溯。

此決策把既有情報能力保留為資料入口，並加入一致的管理物件與後續執行關係，使中台從「看見發生什麼」逐步成為「知道公司正在管理什麼，以及改善到哪裡」。

## 3. 三層架構

### 第一層｜資料層

承接可驗證的事實資料：GoWarehouse、財務、人事、倉容、LINE／Gmail 與人工營運回報。

必要原則：

- 原始來源先保存，再標準化與計算。
- 每筆資料標記來源、版本、觀測時間、匯入批次與品質狀態。
- 來源衝突不得靜默覆蓋，必須進入 Review。
- 事實資料與人工修正分開保存。

### 第二層｜管理層

承接公司要管理的內容：營運問題、SOP、KPI、客戶導入、人員盤點、經營基準與倉庫容量。

必要原則：

- 同一問題只建立一個管理主體，再關聯不同模組。
- 每個管理項目都有狀態、Owner、有效期間、來源、證據、版本與 Audit。
- Baseline、Target、實績與資料品質必須分開。
- 歷史版本保留，不用覆寫目前值的方式消除過往狀態。

### 第三層｜執行層

由人確認後，把管理項目轉成任務，保存負責人、截止日期、狀態、改善結果、證據與追蹤紀錄。

必要原則：

- AI 可以提出候選、摘要與提醒，但不得自行派工、結案或對外承諾。
- 完成必須有結果或證據，不能只靠一句「已完成」。
- 已完成事項可重新開啟；所有轉換保存 Audit。
- 不建立員工自動績效分數或 SLA 處分。

## 4. 第一版六個核心資料模組

1. 倉庫容量
2. 營運問題
3. SOP
4. KPI
5. 客戶導入／Onboarding
6. 人員盤點

第一版先完成資料定義、來源、歷史、查詢、修正、關聯與 Dashboard；執行層在六模組資料品質通過驗收後啟動。

## 5. 來源權威與過渡規則

| 資料類型 | 初始權威來源 | 中台角色 |
|---|---|---|
| 訂單、入出庫、庫存、物流事實 | GoWarehouse／正式匯出檔 | 保存、標準化、品質檢查、計算與關聯 |
| 財務實績 | 核准的財務表或系統 | 保存期間值、版本與口徑，不自行改寫 |
| 人員與組織事實 | 核准的人事資料或人工維護 | 控制權限、有效期間與敏感資料 |
| 倉容與現場觀測 | 倉庫盤點或人工回報 | 保存快照、單位、時間與證據 |
| 管理項目與基準 | 《貨達營運總表》 | 受控承接、版本化、關聯與追蹤 |
| 執行狀態與改善結果 | 中台人工操作 | 成為正式 Audit 與追蹤紀錄 |

當來源權威尚未確認時，資料標記為 `PENDING_AUTHORITY`，不得直接驅動 KPI、提醒或任務。

## 6. Dashboard 原則

- 首頁回答「目前狀態、偏差、風險、資料是否新鮮、有哪些需要確認」。
- 六個模組有獨立頁面與一致的來源／歷史／關聯入口。
- 管理層與執行層分開呈現，避免把「發現問題」誤認為「已經派工」。
- 所有數字可鑽取到公式、期間、來源與明細。
- 已完成或已失效資料仍可依歷史日期查詢。

## 7. 開發順序

資料與能力的原則順序為：**GoWarehouse → 財務資料 → 人工營運回報 → KPI Dashboard → 異常提醒 → 任務／改善追蹤**。每一步通過來源、品質與權限驗收後才擴大下一步。

1. 建立來源清冊、權威範圍、共用欄位、版本與 Audit。
2. 建立總表匯入預覽、欄位對照、衝突 Review 與撤銷。
3. 先做營運問題與 KPI，形成第一個管理閉環。
4. 加入倉庫容量與客戶導入。
5. 加入 SOP 與人員盤點。
6. 完成跨模組關聯與管理 Dashboard。
7. 六模組驗收後，再做人工確認的任務與改善追蹤。

## 8. 此決策不代表

- 不代表立即重做現有 LINE、Gmail、GoWarehouse 或情報功能。
- 不代表營運總表停止維護或立刻全面搬移。
- 不代表 AI 可以自動派工、對外回覆或替管理者結案。
- 不代表所有資料都能自動取得；沒有 API 的來源仍可透過檔案或人工回報，但必須保留批次與資料品質。
- 不代表人員盤點可以轉成自動績效評分。

## 9. 後續文件規則

所有新的 PRD、SDD、資料庫欄位、API、Dashboard 與 Task 必須：

1. 標示所屬層級：資料層、管理層或執行層。
2. 標示所屬核心模組及其權威來源。
3. 定義來源、版本、日期、狀態、證據與 Audit。
4. 說明是否會產生提醒、任務或外部動作，以及由誰確認。
5. 避免建立與既有管理物件重複的平行資料表或頁面。
