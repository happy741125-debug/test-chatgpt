## 1. 產品一句話

Work Intelligence Hub 是貨達的營運資訊蒐集與情報整理系統：從 LINE 工作群組與工作 Gmail 收集日常資訊，理解完整對話脈絡，辨識正在發生的營運事件，再把老闆值得知道、團隊處理中及可忽略的內容整理到 Dashboard。

它不是叫貨工具、聊天紀錄備份工具，也不是現階段的派工／催辦系統。叫貨只是「倉儲營運」領域中的一種事件；Owner、Deadline、Commitment、Blocker 與完成訊號在目前版本都是幫助理解營運狀態的情報欄位。

## 2. 背景與問題

貨達每天的重要資訊分散在多個 LINE 群組與工作 Email：

- 群組訊息量大，重要事件很快被聊天洗掉。
- 單一句訊息通常缺乏完整語意，必須合併前後文才能理解。
- 同一件事可能在不同群組被重複討論。
- 客戶要求、團隊承諾、截止日、案件狀態與阻塞原因散落在長對話中。
- 同一案件常跨數小時或數天，還可能經過改期、取消、人工補救與再次發生。
- 關鍵證據經常藏在圖片、PDF、Excel、物流單或截圖中。
- 管理者若不直接介入群組，很難持續觀察成本、效率、風險與異常。
- 傳統未讀訊息或摘要列表仍要求使用者自行判斷重要性。

產品要把大量訊息轉成少量、可追溯、可理解的營運情報，而不是建立另一個訊息收件匣或另一套工作管理工具。

## 3. 產品目標

### 3.1 核心目標

1. 收得到：可靠接收指定 LINE 群組加入 OA 後的新訊息。
2. 存得住：任何 AI 處理前先保存原始事件與標準化訊息。
3. 看得懂：以一段對話為判斷單位，不逐句誤判。
4. 分得清：辨識貨達的營運領域、事件類型、人物、公司、客戶、專案與商品。
5. 找重點：萃取事件、目前狀態、期限、承諾、阻塞、決策訊號、風險與 FYI。
6. 不重複：把同一事件的多次討論整併成同一張情報卡。
7. 看變化：保留可能負責人、期限、狀態、後續證據與跨日變化；目前不據此自動派工或催辦。
8. 可查證：任何 AI 結論都能回到原始 LINE 訊息與對話脈絡。
9. 少打擾：群組預設靜默；只把真正需要注意的內容送到使用者面前。
10. 附件不漏：圖片、PDF、Excel 等附件能被辨識、關聯並逐步理解內容。

### 3.2 資訊層成功狀態

使用者每天不用逐一翻閱 LINE 群組，也能從 Dashboard 回答：

- 今天貨達發生了什麼重要事情？
- 哪些異常可能影響出貨、客戶、成本或人力？
- 哪些事情值得我知道，哪些可能需要決策？
- 團隊答應了什麼、目前做到哪裡、卡在什麼地方？
- 哪些事情團隊正在處理、我暫時不用介入？
- 哪些問題在不同客戶或不同時間反覆發生？

## 4. 非目標

目前情報層不做：

- Google Chat、Slack、Teams、WhatsApp、Telegram 等其他訊息來源。
- 自動回覆 LINE 群組。
- 自動寄信、替使用者做決策、指派員工、對外承諾或自動催辦。
- SLA 執法、員工績效評分、完整客戶導入工作流、建立 Calendar、修改 WMS／ERP 或執行財務動作。
- 回溯 OA 加入群組前的 LINE 歷史訊息。
- 用低可信度 AI 結果直接觸發不可逆行動。

## 5. 主要使用者

### 5.1 核心使用者：管理者／Founder

需求：不必介入所有群組，仍能掌握貨達正在發生什麼、哪些值得注意，以及事件如何變化。

### 5.2 次要使用者：營運主管

需求：查看異常、承諾、阻塞與跨群組重複事件，補充或修正情報。

第一版可先以單一核心使用者設計，但資料模型需保留未來多使用者與權限擴充空間。

## 6. 產品原則

1. **情報優先，不是訊息優先**：首頁呈現事件、狀態與變化，而不是未讀訊息列表。
2. **貨達領域優先**：先判斷事件屬於哪個營運領域，再判斷情報類型。
3. **對話脈絡優先**：AI 分析 Conversation Context，而不是孤立句子。
4. **證據優先**：每張情報卡都能查看來源。
5. **保守自動化**：低可信度進 Review Queue，不自動做確定陳述。
6. **群組安靜**：LINE 群組預設 Silent Mode。
7. **人可修正**：使用者可調整分類、人物、期限、優先級、狀態與合併結果。
8. **來源共用核心**：LINE-first；Gmail 作為第二資料來源，兩者共用 Context、分類、去重與摘要能力。
9. **先理解、後管理**：先把資訊收集與判讀做好，再考慮派工、催辦、SLA 或績效功能。

## 7. 貨達 Domain Layer

每件情報先歸入營運領域，再標記事件類型與 Intelligence Type。

### 7.1 營運領域

| Domain | 說明 | 事件例子 |
|---|---|---|
| Warehouse Operations | 倉儲與出貨日常 | 缺貨、叫貨、揀貨、錯出、延誤、盤點差異、庫存異常 |
| Customer | 客戶關係與服務 | 客訴、需求變更、服務異常、續約、流失風險 |
| Sales | 業務與商務進度 | 新客戶、報價、提案、合約、成交進度 |
| Finance & Cost | 財務與成本 | 人事費、耗材、物流費、租金、加班費、異常支出、現金流 |
| People | 人員與排班 | 請假、缺工、加班、人力調度、衝突、訓練 |
| Alliance Warehouse | 聯盟倉合作 | 新據點、導入進度、合作倉異常、SOP 落差 |
| System | 系統與資料 | WMS、訂單、API、串接、權限、資料錯誤、服務中斷 |
| Management | 管理事項 | 跨部門卡點、主管承諾、需要決策、未完成追蹤 |

### 7.2 Intelligence Facet

| Type | 定義 |
|---|---|
| EVENT | 已發生或正在發生的營運事件 |
| TASK | 對話中出現明確行動訊號；目前只作為情報標籤，不自動派工 |
| COMMITMENT | 某人明確答應的交付或行動；目前只保存承諾內容與時間 |
| DECISION | 已形成的決策 |
| DECISION_REQUIRED | 需要使用者或主管決定 |
| RISK | 可能造成營運、客戶、財務、人事或系統影響 |
| FOLLOW_UP | 未來值得再確認的資訊訊號；目前不自動催辦 |
| FYI | 值得知道但暫時不需行動 |

同一段 Context 可判讀出多種 Intelligence Facet，但同一營運案件在 Dashboard 只顯示一張主卡。例如缺貨事件的「風險、補貨行動、到貨承諾」會成為同一主卡內的標籤與理解依據，不分裂成多張卡、也不各自計算不同重要度。

## 8. 核心範圍：資訊蒐集與情報整理

### 8.1 LINE Data Foundation

- 專屬 LINE OA 加入指定工作群組。
- 驗證 Webhook Signature。
- 保存 Raw Event，再標準化成 Message。
- 以平台與外部訊息 ID 保證冪等，不因 Webhook 重送而重複處理。
- 辨識群組、使用者、訊息時間與訊息型態。
- 保存附件類型、名稱、來源與可查證關聯；附件內容理解逐步加入。
- 支援群組啟用／停用與監控等級。
- 收訊與 AI 分析分離；AI 故障不得影響訊息保存。
- 群組預設 Silent Mode，不主動回覆。

### 8.2 Conversation Context

- 以時間窗、訊息數量與群組界線建立 Context。
- 預設 2–5 分鐘 Buffer，搭配約 5–15 分鐘或前後 10–30 則訊息。
- 對跨日案件建立 Continuation Candidate，不能只因超過時間窗就視為新事件。
- 補入人物、群組、時間與已知實體資料。
- 高風險訊息可走 Urgent Bypass，但仍需保留足夠上下文。
- 每個 Context 可回溯所有來源 Message。

### 8.3 AI Intelligence

- 判斷工作資訊或雜訊。
- 萃取領域、事件類型、Intelligence Facet、標題、摘要、人物、公司、客戶、專案、商品、訂單、平台、數量、可能負責人、期限、承諾、狀態、阻塞原因與風險。
- 所有模型結果必須是通過 Schema 驗證的結構化資料。
- 保存模型、Prompt 版本、用量、信心分數與錯誤資訊。
- 低信心結果進 Review Queue，不直接通知。

### 8.4 Priority、Dedup 與狀態訊號

- 每個營運案件只計算一組 0–100 Priority Score 並映射 P0–P3；卡內所有 Intelligence Type 共用同一重要度。
- 區分 BOSS／TEAM／NOISE，表示管理者注意程度，不代表系統已指派工作。
- 同一事件的新訊息應更新既有主卡並附加來源，不重建多張卡；訂單、入庫單、加工單等強識別碼優先，無編號案件則以客戶、領域、主題、狀態與時間保守比對。
- 保存要求日期、承諾日期、目前狀態與阻塞類型，作為資訊摘要依據。
- AI 可依事件階段標示 LIKELY_DONE，只有使用者確認後才成為 DONE；「已入庫」不得誤判為整個出貨案件完成。

### 8.5 Dashboard

首頁 Today 以注意層級為核心，並可沿用下列資訊區塊：

- 需要你決定
- 需要你處理
- 需要追蹤
- 風險
- 團隊處理中
- 值得知道

另外提供：

- Intelligence Feed 與條件篩選。
- 情報詳細頁與來源時間軸。
- 修改分類、人物、期限、優先級與狀態。
- 合併、歸檔、Feedback 與 Audit Log。
- 低信心與疑似重複的 Review Queue。

## 9. LINE 群組監控等級

| 等級 | 行為 |
|---|---|
| A — Critical | 所有新訊息進分析流程 |
| B — Normal | 分析工作資訊，略過大量一般聊天 |
| C — Low | 只保留明確任務、異常、決策、Deadline 或 @mention 等訊號 |
| D — Ignore | 保存必要連線狀態，但不做內容分析；可依隱私政策決定是否完全不保存訊息 |

## 10. Priority Model

建議初始權重：

| 因素 | 最大分數 |
|---|---:|
| 需要使用者行動／決策 | 30 |
| 緊急性 | 20 |
| 營運影響 | 20 |
| 風險程度 | 15 |
| 來源權威性 | 5 |
| Deadline 接近程度 | 5 |
| 重複出現／持續惡化 | 5 |

Priority Level：

- P0 Critical：立即關注，例如重大出貨事故、法律事件、大額財務異常、系統全面故障。
- P1 High：當天值得管理者優先知道，例如可能影響出貨、客戶、財務或系統。
- P2 Medium：近期需知道或追蹤。
- P3 Low：FYI。

規則型 Critical Event 不得被個人偏好降級。

## 11. 核心使用流程

### 11.1 收集到情報

LINE／Gmail 新訊息 → 驗證與同步 → Raw Event 保存 → Message 標準化 → Queue → Context 組裝 → AI／規則分析 → Domain／Entity 對應 → Intelligence 建立或更新 → Priority／Dedup／State Signal → Dashboard。

### 11.2 查看與修正

使用者開啟 Today → 查看 BOSS／TEAM／NOISE 與風險摘要 → 開啟情報卡 → 查看來源對話與事件變化 → 修正分類、合併或狀態 → 系統保存 Feedback 與 Audit Log。

### 11.3 例子

原始對話：「今天 A 客戶的貨差 20 箱，已經請 Kevin 跟廠商叫貨，預計明天下午到。」

系統應整理為：

- Domain：Warehouse Operations
- Event Type：庫存不足
- 客戶：A
- 缺口：20 箱
- 可能負責人：Kevin
- 行動訊號：向廠商補貨
- 承諾訊號：預計明天下午到貨
- RISK：可能影響出貨
- attention_level：若團隊可處理則為 TEAM；若可能影響重大客戶或需要決策則為 BOSS

## 12. 第二資料來源：工作 Gmail（進行中）

Gmail 在 LINE 基礎閉環後接入，目前作為第二資料來源：

- Google OAuth 最小必要 Read Only 權限。
- 初始同步與增量同步。
- Email Thread 為分析單位。
- HTML 清理、簽名與引用舊文移除。
- 判斷 Primary、CC、Forward、System、Newsletter、Marketing、Automated。
- 萃取事件、狀態、承諾、期限、阻塞與注意層級；「需回覆」只作為資訊訊號。
- LINE 與 Gmail 身分整併、跨來源事件合併與共同來源時間軸。

Gmail 不另建一套情報邏輯，而是共用既有 Context、Entity、Intelligence、Priority、Dedup 與 State Signal 核心。

## 13. 安全、隱私與信任

- 驗證 LINE Signature，拒絕偽造事件。
- Secret 不寫入程式碼或 Log。
- 原始訊息、AI 結論與人工修改均有存取控制。
- 保存期限與刪除政策必須可設定。
- 敏感內容在 Log 中遮罩。
- 電話、地址、Email、金額、訂單、邀請網址、密碼與附件內容依角色遮罩；公開 Repo 與測試資料只能使用去識別化內容。
- AI 結論必須附來源與信心分數。
- 大金額、重大客訴、法律、人事衝突、高階主管承諾與 Critical Event 若信心不足，使用「可能」措辭並進人工確認。
- 群組不主動回覆，降低洗版與資訊外洩。

## 14. 成功指標

### 14.1 系統指標

- 合法 LINE Webhook 接收成功率 ≥ 99.9%。
- Webhook 重送造成的 Message 重複率 = 0。
- AI 故障時原始訊息遺失率 = 0。
- 每張正式 Intelligence 可追溯來源比例 = 100%。
- P0/P1 通過結構驗證與規則檢查比例 = 100%。

### 14.2 情報品質指標

- Work／Noise 分類 Precision ≥ 90%。
- 高優先事件 Precision ≥ 85%。
- Entity、Deadline、Status、Blocker、Domain 與 Type 各自可量測並建立基準線。
- 自動合併採保守策略，錯誤合併率優先低於漏合併率。
- 以 200–500 組去識別化真實 Context 建立 Golden Dataset 與回歸測試。

### 14.3 產品指標

- 使用者可在 10 分鐘內完成每日營運掃描。
- 使用者不需回看原始群組即可理解大部分情報，但可一鍵查證。
- 重要事件、承諾、Deadline 與狀態變化的漏收量持續下降。
- 每日摘要能說明「新增、變更、惡化、可能完成」，不重複列出未變事件。
- 使用者對「不重要」的負回饋比例逐版下降。

## 15. 資訊層驗收標準

1. OA 加入測試群組後，可接收並保存新訊息。
2. 無效 Signature 被拒絕；相同 Webhook 重送不重複建立資料。
3. AI 停機時訊息仍保存在 DB，恢復後可重跑。
4. 「貨到了嗎／還沒／廠商說星期四」形成一個 Context，不是三個孤立事件。
5. 缺貨案例能同時辨識事件、行動、承諾與風險訊號，且 Domain 為倉儲營運。
6. 同一事件跨訊息、跨日或跨來源出現時，保守更新同一張卡並附加來源；不確定時進人工 Review。
7. Dashboard 能清楚區分 BOSS、TEAM 與 NOISE。
8. 任何卡片可查看來源訊息、模型版本、信心與修改紀錄。
9. 群組在一般情況下完全不回覆。
10. 「已入庫但待出貨」不得被判為整案完成；問題、否定句與部分完成需保守處理。
11. 圖片、PDF、Excel 等附件至少保留可查證的類型、名稱、來源與案件關聯。

## 16. 依賴與待確認事項

- LINE OA Channel Secret、Access Token 與 Webhook 公開網址。

- P0 通知是否在第一版啟用；若啟用，預設只傳管理者 OA 私訊。
- AI Provider、可接受月成本與資料處理規範。
